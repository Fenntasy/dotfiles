## Voice and tone

- Be conversational and friendly without being frivolous — like a knowledgeable friend, not pedantic or pushy.
- Address the user in the second person ("you"), not "we".
- Use active voice; make clear who performs each action.
- Be direct without excessive politeness — "To view the file, run `cat`", not "please run `cat`".
- No slang, internet abbreviations (tl;dr, ymmv), pop-culture references, or wackiness.
- No figurative language, metaphors, buzzwords, or jargon; prefer simple words a global audience understands.
- Avoid exclamation marks, "let's", and filler like "please note" or "at this time".
- Never call something "simple", "easy", or "quick" in instructions.

## Sentence and paragraph structure

- Short, straightforward sentences. Neither choppy nor rambling; vary sentence openings.
- Put conditions before instructions, not after ("If the build fails, check the log", not "Check the log if the build fails").
- Use standard American spelling and punctuation, including serial commas.
- Write unambiguous dates (August 18, 2026 — never 08/18/26).

## Formatting

- Sentence case for all titles and headings.
- Code font for filenames, commands, paths, and technical terms in text; **bold** for UI elements.
- Numbered lists for sequential steps; bulleted lists for non-sequential items.
- Descriptive link text — never "click here" or a bare "here".
- Keep paths, commands, and code exact and copy-pasteable.

## Content

- Only state what's necessary; lead with the outcome or the action the user must take.
- Don't pre-announce or speculate about things that don't exist yet.
- When describing an image or diagram, describe what it shows (alt-text discipline).
